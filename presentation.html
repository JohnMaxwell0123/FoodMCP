Market Pain Points
现有方案的三大痛点
现有B站探店小程序的信息粒度和检索能力远不能满足用户真实需求
📊

维度单一，菜品信息缺失

仅有"餐厅"级数据，用户想了解某道菜的评价，必须自行翻看完整视频。

🔍

搜索僵化，无法理解意图

只支持城市、UP主筛选。无法处理"锅气足、大肠处理干净的鲁菜馆"这类需求。

⚠️

负面评价被系统性忽略

UP主说"爆炒腰花火候欠佳"，在现有工具中完全无法体现，用户依然踩雷。

MCP Skills
核心 MCP Tools 设计
标准化 MCP 接口，任何 AI Agent 都能调用；每个返回值都带出处，引用规范写在 Tool 描述里。5 个查询，1 个回写
01

按评价语义搜菜品

search_dish_by_semantic_review

按自然语言描述检索菜品，每条结果附 UP 主原话、视频链接（带时间点）与核验状态；可以只查 UP 主说别点的菜。

示例查询 "北京，红烧肉要肥而不腻，有UP主认证过的"
02

餐厅证据分布

get_restaurant_detailed_review

每道菜按 UP 主计票，标注孤证、共识、争议，不输出平均分。

示例查询 "这家店哪些菜被多位 UP 主点名？有没有人说别点？"
03

餐厅横向对比

compare_restaurants

优先比较两家都去过的 UP 主（同一个人的标准更可比）；样本不足时不下结论。

示例查询 "这两家涮肉，哪家更稳？"
04

UP 主口味画像

get_up_taste_profile

城市足迹、常探菜系、判定分布与代表性原话；"选择性"只描述表达风格，不代表可信度。

示例查询 "这位 UP 主常吃什么？推荐率是多少？"
05

生成美食打卡路线

generate_food_tour_itinerary

按高德坐标编排路线；必点、避雷与原话只取自证据数据，LLM 新增的内容会被自动删除。

示例查询 "北京两天一夜、以老字号为主的路线"
06

餐后反馈回写

report_dining_outcome

Agent 在下一次对话里代收用户吃完的感受，挂在具体的那条 UP 主说法上；累计成每位 UP 主按菜系拆分的一致率。唯一会写入数据的工具。

示例对话 "上次那家的鱼确实嫩，但藿香烧米翘不值"

📋 真实运行产物节选 — 餐厅「8.4优雅河鲜」

菜品 价格 判定 UP主原话（节选）
一帆风顺（鱼） ¥298/斤 推荐 "这鱼肉真的好嫩……吃到最后还是有一点点土腥味，我能尝出来，你们不一定。"
生态白胡子（豆豉做法） ¥598/斤 一般 "鱼的品质还是不错的……但 598 的花拉丁，价格版的顶配奥拓，它也是奥拓呀。"
乡村藿香烧米翘 ¥198/位 踩雷 "198 块钱，两块鱼肉一疙瘩面，而且你这个位置也没给我选好。"

这三条都不是 UP 主撒谎，难点在"话该怎么读"：专家才吃得出的瑕疵、取决于预算的好坏、混进菜品判断的店级因素。

Trust by Design
可信设计：凭什么可信
不假设 UP 主更诚实，而是让每个判断都可以被核对、被反驳、被计数。
🔎

原话可核对

原话入库前回查字幕，对上的记录视频时间点与跳转链接，对不上的标为未核验。离线评测与线上核验用同一套规则。

📊

不输出平均分

每位 UP 主一票，标注孤证、共识、争议；对比优先看两家都去过的 UP 主，样本不足时不下结论。

⚖️

负面结论举证更高

避雷榜只收原话已核验的踩雷；判定宁轻勿重，不替一个有名有姓的人加重语气。

🦆 对照美团鸭觅

  • 鸭觅回答"该信谁"：筛选并问责推荐官，结论压缩成几把金勺子。
  • FoodMCP 回答"凭什么信"：不选人，把信任押在证据上，每条结论都能追到原视频的那一秒。
  • 形态互换以后，两者断在同一个地方：数据层拿不到餐后反馈。所以 FoodMCP 加了回写工具 report_dining_outcome，让 Agent 代收餐后反馈；接下来缺的是真实使用。
  • 机制对照与形态互换的思想实验见 PORTFOLIO 第七章。
