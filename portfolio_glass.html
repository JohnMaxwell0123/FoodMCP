02 — Product & Architecture
从视频到 Agent，一条全自动 Pipeline

不直接服务 C 端，而是通过 MCP 标准协议赋能所有 AI Agent —— 平台型产品的杠杆选择。

Consume AI Agent 消费层 — Claude / ChatGPT / 自研 Agent，经 MCP 协议（JSON-RPC）调用
Serve MCP Server — 3 个 Tool：语义搜索菜品 · 餐厅深度点评 · 美食行程规划
Store 三库架构 — Milvus 语义向量检索 · Neo4j 评价关系图谱 · PostgreSQL 结构化元数据
Pipeline 数据管线 — B站采集 → 探店筛选 → 字幕提取 → LLM 抽取 → 清洗校验 → 高德地理编码 → 三库写入
1

语义搜索菜品

search_dish_by_semantic_review

自然语言口味描述 → 向量语义匹配 → 菜品 + UP 主评价原文。支持城市、情感倾向、UP 主过滤。从「搜餐厅」到「搜口味」的范式升级。

2

餐厅深度点评

get_restaurant_detailed_review

PostgreSQL + Neo4j 联合查询，聚合多 UP 主评价，输出菜品级好/差评统计与评价原文。解决信息碎片化。

3

美食行程规划

generate_food_tour_itinerary

LLM + 高德地理数据 + 评价数据 → 多日打卡路线，标注每店必点菜与避雷菜。从「查信息」到「做决策」的价值延伸。

关键决策 — 为什么是 MCP 而不是小程序 / REST API MCP 是 AI Agent 工具调用的标准协议，可类比「AI 世界的 USB 接口」。任何支持 MCP 的 Agent 都能零开发成本调用本服务。自建小程序意味着获客与维护的重投入；REST API 与 Agent 对接仍需适配。选择 MCP 是把产品边界主动划定在生态杠杆最大处。

04 — AI Product Strategy
不是调 API，是完整的 AI 产品设计闭环

LLM 在本项目中不是 feature，而是核心引擎——围绕它的每一个决策都是产品决策。

环节技术选择产品决策逻辑
信息抽取DeepSeek-Chat成本约为 GPT-4o 的 1/10，中文口语理解强，适合批量处理字幕文本
向量化OpenAI text-embedding-3-small中文语义检索效果稳定；独立 API Key 架构，Embedding 与 LLM 可独立替换
Prompt 工程3 套专用模板角色具体化（「专业美食视频分析师」）+ JSON Schema 强约束 + 枚举限定 + 负样本显式要求（「不要遗漏任何踩雷信息」）
质量保障置信度评分体系Schema 校验 → 字段完整性检查 → 置信度打分 → 低分标记人工复核；verdict 自动规范化（「好吃推荐」→ 推荐）
数据架构PG + Neo4j + Milvus单库无法同时满足精确查询 + 关系分析 + 语义理解；以架构复杂度换取检索性能与灵活性
MVP 策略 — 先验证最难的假设

不追求覆盖量，先验证最关键一环：「非结构化视频 → 结构化数据」能否稳定跑通。这一环用真实数据验证通过后，才谈规模化。采集规模（60 视频）与抽取验证规模（2 视频端到端）的区分是刻意的风险控制，而非能力不足。

核心数据单元 — Review

UP 主原话（非摘要，保留真实声音）· 情感三分类（推荐/一般/踩雷）· 五维度细分（口味/口感/分量/卖相/性价比）· 来源 BV 号 + 时间戳（可跳转验证）。一条评价连接 UP主、菜品、餐厅、视频四个维度，全链路可追溯。

做 AI 产品最难的不是「能不能用 AI」，而是搞清楚 AI 在这个场景下到底创造了什么增量价值。不是把 AI 当 feature 加上去，而是找到 AI 能让原本 impossible 的事情变成 possible 的那个点。 Core Belief · 核心产品认知
